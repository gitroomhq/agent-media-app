Zero-Issues Reliability Plan

agent-media · production system (3,000+ paying users) · drafted 2026-06-02

Goal: nothing the user does ends in a silent stop or a dead-end. Every error is (1) captured with full context, (2) routed to a human in realtime, (3) recoverable for the user (retry/refund/clear message), and (4) tracked to closure. "0 issues" is an operational discipline — capture → alert → recover → close — not a one-time fix.

2 · The four things you asked to track

① User errors — every thrown exception & failed run, with the user id, run_id, inputs (PII-scrubbed), and the existing error_code attached. → Sentry on all four surfaces + DB run-failure ingestion.
② Realtime issues — crashes, error-rate spikes, queue stalls, provider outages, health-check failures. → Sentry alert rules → Slack + an uptime/synthetic monitor + a worker dead-man's-switch.
③ Open bugs — a single triage board where every captured issue lands, gets owned, and is tracked to closed. → Sentry Issues as source of truth, mirrored to Linear/GitHub for the ones we fix; weekly triage ritual.
④ User reportings — an in-app "Report a problem" widget that auto-attaches session, current run_id, and last error, writes to a bug_reports table, and pings Slack. Closes the loop the user can't otherwise see.

3 · Phased rollout (sprint-able)

0
Critical · do first

Baseline visibility — see every error

  • Sentry across all 4 surfaces: @sentry/nextjs (web, incl. source maps + session replay on errors), @sentry/node (api-v2 + worker), Sentry Deno SDK / manual capture (edge fns).
  • Wire releases to the git SHA (we already deploy per-commit) so every error maps to a deploy + is source-mapped.
  • Attach user context (user id, plan, run_id) + scrub PII (emails, ma_ keys, prompts flagged sensitive) in beforeSend.
  • Ingest DB run failures (status='failed' + error_code) into Sentry so backend pipeline failures show up next to crashes.
1
Critical

Crash-proof the backends — no silent stops

  • api-v2: global Express error handler + process.on('uncaughtException'/'unhandledRejection') (capture → Sentry → graceful shutdown, never a half-dead process).
  • Correlation ID (request_id) generated at the edge, threaded web → api-v2 → worker → logs, returned in error responses so a user report maps to exact traces.
  • Structured logging (pino) replacing ad-hoc console; one log shape across services.
  • Graceful Temporal worker shutdown + retry/heartbeat audit so a deploy never drops an in-flight render (we hit this before).
  • Per-segment React error boundaries + global-error.tsx (layout crashes) + client-side exception capture.
2
Realtime issues

Alerting + on-call — a human hears about it instantly

  • Sentry alert rules → Slack: new issue, error-rate spike, regression after deploy.
  • Uptime/synthetic monitor (Better Stack or Checkly) on /health (api-v2 + worker) + the public site.
  • Worker dead-man's-switch: alert if the Temporal queue has 0 completions in N min while jobs are queued (catches the crash-loop class we've hit).
  • Provider-outage signal: surface the worker's PROVIDER_* codes as a metric → alert when any provider error-rate crosses a threshold.
3
User reporting + recovery

The user is never stuck

  • In-app "Report a problem" widget → writes bug_reports (user, run_id, route, last error, console tail) + Slack ping + Sentry user-feedback link.
  • Auto-recovery by error_code: PROVIDER_BUSY/TIMEOUT/CIRCUIT_OPEN → automatic retry; CONTENT_POLICY_BLOCKED → clear "edit your prompt" message; any credit-charged failure → auto-refund + visible note.
  • Clear failure UX: every error_code maps to a friendly message + next action (retry / change input / contact) — no raw stack, no dead spinner. (Agent + skills + gallery.)
4
Proactive zero-issues

Catch it before the user does

  • Synthetic E2E monitor running the real critical flow (login → generate short clip → deliver) every N min against prod; page on failure.
  • SLOs + error budget: e.g. 99.5% run success, p95 render time, <0.1% 5xx — tracked on one dashboard.
  • Single "Issues" dashboard (Sentry + DB run-failure rate + queue depth + provider health) — the one screen that answers "is anything broken right now?".
  • Weekly triage ritual: every open issue owned or closed; error budget reviewed.
5
Hardening

Keep it at zero

  • Public/internal status page fed by the monitors.
  • CI regression guards: the E2E journeys run on every deploy (block promote on red); type/lint already gate.
  • Load & light chaos tests on the render pipeline; circuit-breaker tuning.
