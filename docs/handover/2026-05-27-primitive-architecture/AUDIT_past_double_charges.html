Past double-charges — audit

100% read-only. Two SELECTs, no writes. Safe to run on production. This only measures the damage — refunding is a separate decision after we see the numbers.

How it detects a double-charge: one legitimate deduct_credits call can write up to two rows (monthly + purchased bucket) sharing the same created_at. A retry is a separate call seconds later with a different created_at. So we group debit rows into charge events by (reference_id, created_at), then flag any job with more than one event.

Query A — blast radius (summary)

WITH events AS (
  SELECT reference_id, user_id, created_at, SUM(ABS(amount)) AS event_credits
  FROM public.credit_transactions
  WHERE type = 'generation_debit' AND reference_id IS NOT NULL
  GROUP BY reference_id, user_id, created_at
),
dups AS (
  SELECT reference_id, user_id,
         COUNT(*)              AS charge_events,
         SUM(event_credits)    AS total_charged,
         MAX(event_credits)    AS legit_charge
  FROM events
  GROUP BY reference_id, user_id
  HAVING COUNT(*) > 1
)
SELECT
  COUNT(*)                               AS jobs_double_charged,
  COUNT(DISTINCT user_id)                AS users_affected,
  SUM(charge_events - 1)                 AS extra_charge_events,
  SUM(total_charged - legit_charge)      AS surplus_credits_overcharged
FROM dups;

Query B — per-user breakdown (who to refund)

WITH events AS (
  SELECT reference_id, user_id, created_at, SUM(ABS(amount)) AS event_credits
  FROM public.credit_transactions
  WHERE type = 'generation_debit' AND reference_id IS NOT NULL
  GROUP BY reference_id, user_id, created_at
),
dups AS (
  SELECT reference_id, user_id,
         COUNT(*) AS charge_events,
         SUM(event_credits) - MAX(event_credits) AS surplus
  FROM events
  GROUP BY reference_id, user_id
  HAVING COUNT(*) > 1
)
SELECT user_id,
       COUNT(*)       AS jobs_affected,
       SUM(surplus)   AS surplus_credits_owed
FROM dups
GROUP BY user_id
ORDER BY surplus_credits_owed DESC;

Caveats to sanity-check in the output: (1) if credit_transactions uses a timestamp column other than created_at, swap the name. (2) Refunds that already happened (type='generation_refund') are not netted here — if Query A shows a meaningful number, the next step is a refined query that subtracts existing refunds before computing what's still owed.
