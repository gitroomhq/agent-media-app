Both gap 1 and gap 2 touch production user-visible surfaces (the dashboard reads from generation_jobs and credits decrement is the real money ledger). Per the operating rules I want an explicit "go" on the plan below before I push.

Gap 1 — vNext runs missing from the dashboard / gallery

Today

apps/web/app/(app-dark)/dashboard/page.tsx queries Supabase directly:

supabase.from('generation_jobs')
  .select(...)
  .eq('status','completed')
  .order('created_at', desc)
  .limit(60);

vNext writes to primitive_runs + skill_runs + primitive_artifacts. The dashboard never queries those, so my runs are invisible.

Plan

  1. Add a new api-v2 endpoint GET /v1/me/gallery?limit=20 that returns the user's recent generations from BOTH sources in one merged, date-sorted list. Service-role under the hood, scoped by user_id from the bearer token.
    Each row has: id, source ("legacy" | "vnext_primitive" | "vnext_skill"), kind (portrait/character_sheet/selfie_video/composed_video), thumbnail_url, media_url, created_at, status, duration_seconds.
  2. Patch the home dashboard apps/web/app/(app-dark)/dashboard/page.tsx to call /v1/me/gallery through invokeFn or a fetch with the user's Supabase JWT. Drop the direct generation_jobs query. Same grid renders; the filter (video files only) keeps working because vNext videos end in .mp4.
  3. Patch the gallery page apps/web/app/(dashboard)/gallery/page.tsx + apps/web/app/(app-dark)/dashboard/gallery/page.tsx with the same swap. Detail page (gallery/[id]/page.tsx) gets a branch to load by primitive_run_id / skill_run_id when source is vNext.

Risk

Frontend deploys auto on push to main via Vercel. If the new endpoint returns badly, the home + gallery break. Mitigation: the patched pages fall back to the legacy query on error, so worst case the user sees only legacy entries (same as today).

Gap 2 — vNext credit ledger not wired

Today

Legacy generations call the Postgres RPC deduct_credits(user_id, amount, job_id, description) at submit (see services/api-v2/src/routes/v2/selfie.ts + generate.ts). Refund on failure via re-add transaction. actual_credits_usd in primitive_runs is independent and doesn't touch the user's 1,902-credit balance.

Pricing alignment

1 credit ≈ $0.006 (Pro Plus = 1,902 credits ≈ $11.41 monthly). vNext primitive USD → credits:

PrimitiveUSD estimateCredits
portrait_gpt2$0.2035
character_sheet_gpt2$0.2035

simple_selfie 15s$1.80300
make_ugc_video 5s (full)~$1.00~170 (35 + 35 + 100)

Plan

  1. Deduct at submit from the api-v2 routes — same pattern as legacy. Pre-flight check: if balance < estimated cost, return 402 BEFORE workflow start.
  2. Pass p_job_id = primitive_run_id for primitive-level skills (make_portrait, make_character_sheet, make_simple_selfie). For make_ugc_video, deduct each step's credits as it completes — needs a small refund/reconcile Activity inside the workflow.
  3. Refund on terminal failure: the worker, when the Activity raises a non-retryable budget/SSRF/validation error, calls an api-v2 refund endpoint that inserts a reverse credit_transactions row.
  4. Audit: add credits_deducted column to primitive_runs (small migration) so the ledger can be reconciled per primitive.

Risk

If I get the math wrong users get over-charged. Mitigation: log the deduction + the inputs, ship a one-liner verifier script. Start with conservative estimates above.
