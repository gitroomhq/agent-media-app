Micro-skills — design

What a "micro-skill" is here

A micro-skill is the smallest user-facing unit in the Skill Center. It's a named, versioned wrapper around exactly one primitive. Same Temporal workflow, but it gets a public name, slug, default inputs, and shows up in GET /v1/skills.

Future composed skills (e.g. "make UGC video") will chain multiple primitives. Micro-skills are the 1:1 building blocks.

How it's wired (minimal, no premature abstraction)

  • Skill registry — in-code map for V1, not a DB table. services/api-v2/src/skills/registry.ts exports a SKILLS object keyed by slug. Each entry has: name, version, description, primitive id, Zod input schema (re-uses the primitive contract), Temporal workflow type, output shape. Same shape we'd later persist to a skills table when the marketplace lands.
  • Two API routes in api-v2 (both feature-flagged behind VNEXT_PRIMITIVES_ENABLED):
    • GET /v1/skills — lists registered skills (slug, name, version, description, JSON-schema'd input).
    • POST /v1/skills/:slug/run — validates input against the registry's schema, mints a primitive_run_id, starts the underlying primitive workflow on the primitive-vnext-v1 queue, returns {run_id, workflow_id, skill: slug, status: "submitted"}. Same Idempotency-Key handling as the primitive routes.
  • No new DB tables. Skill runs map 1:1 to primitive_runs for now. A skill_runs table lands when composed skills (multi-step graphs) appear.
  • No new worker code. Skill workflow == primitive workflow for micro-skills.

Sample call

curl -X POST https://api.agent-media.ai/v1/skills/make_character_sheet/run \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: sara-cs-1" \
  -d '{
    "portrait_url": "https://pub-...r2.dev/vnext/primitive-runs/.../portrait.png",
    "description": "Sara, 28 years old"
  }'

→ 202 { run_id, workflow_id, skill: "make_character_sheet", status: "submitted" }
