Credit double-charge on retry — fix

Root-cause fix for the HIGH-severity billing bug. Production, 3000+ paying customers.

The bug

  • vNext primitive Activities retry up to 3× (maximumAttempts: 3).
  • deduct_credits is called near the top of each Activity, before the provider call.
  • The old deduct_credits had no guard against being called twice for the same job, and the Activity's "skip if done" guard only fires on status='succeeded'.
  • So any retryable failure after the deduct line (OpenAI 5xx, R2 blip, transient DB error) re-ran the Activity and charged the user again — 2–3× on a run that eventually succeeds, with no refund (refund only fires on non-retryable terminal failures).
Evidence: workflows/portrait-gpt2.ts:17, activities/portrait-gpt2.ts:76,157, client/credits.ts:65, migrations/20260216000015_deduct_credits.sql (no dedupe).

The fix

Make deduct_credits idempotent on p_job_id: after locking the user_credits row, if a generation_debit already exists for that job, return current balances as an idempotent replay without charging again. This mirrors refund_credits, which already guards double-refund the same way. Everything else is byte-for-byte identical to migration 015.

p_job_id is a fresh UUID per run and never reused, so legitimate separate charges are unaffected — only retries of the same job collapse to one charge. It's the single chokepoint all callers share (vNext primitives and legacy generations), so the fix protects both.
